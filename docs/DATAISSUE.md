# DATAISSUE.md — 더미데이터 정합성 문제 목록

`pet_reco.db`(= `data/*.csv` 적재본)에서 발견된 정합성 문제를 정리합니다.
**더미데이터를 재생성하는 사람에게 넘기는 명세**이자, 재생성 후 무엇을 확인해야 하는지의 기준입니다.

> 이 문서가 필요한 이유는 **데이터가 어긋나도 파이프라인이 에러를 내지 않기 때문**입니다.
> FK 조인은 `pet_id`로 조용히 성립하고, `build_index.py`는 읽은 값을 그대로 문장으로 만들어
> 인코딩합니다. 모순된 행이 아무 경고 없이 벡터가 되고, 그 벡터가 RAG 근거로 LLM에 넘어가
> 모순된 답의 재료가 됩니다. 검색 결과를 눈으로 보기 전까지는 아무도 모릅니다.

## 검사 방법

```bash
python src/load_db.py
python src/check_data.py     # 이 문서의 모든 항목을 자동 검사
```

`src/check_data.py`가 11개 검사를 `ERROR` / `WARN` 두 단계로 판정합니다.
`ERROR`가 하나라도 있으면 exit code 1이므로, 태스크 체인에 넣으면 색인 전에 자동으로 멈춥니다.

- **ERROR** — 이 상태로 색인하면 잘못된 근거가 만들어집니다. 고치기 전에는 진행하면 안 됩니다.
- **WARN** — 알고는 있어야 하지만 색인을 막을 정도는 아닙니다. 설계 미확정이거나 소수 사례입니다.

## 1. `pet_purchases`와 `pet_profiles`가 서로 다른 데이터 ← 최우선

`pet_purchases`에는 리뷰 작성 시점의 반려견 상태(`breed`, `size_category`, `weight_kg`,
`allergy`)가 **의도적으로 비정규화**되어 있습니다. 프로필은 시간에 따라 변하지만 리뷰는
"그때 그 강아지"의 이야기여야 하기 때문입니다(`src/src.md`).

더미데이터는 시간 변화를 모사하지 않으므로 두 값이 **같아야 정상**입니다. 그런데:

```
breed 불일치       1383 / 1439  (96.1%)
weight_kg 불일치   1422 / 1439  (98.8%)
allergy 불일치      885 / 1439  (61.5%)
```

예: `O00001`은 구매 기록상 `토이푸들`인데 프로필상 `시츄`입니다.

### 근거 — 견종 어휘가 겹치지 않습니다

| 구분 | 종수 | 견종 |
|---|---|---|
| `pet_purchases` 전용 | 8 | 도베르만, 미니어처닥스훈트, 셰퍼드, 요크셔테리어, 코커스패니얼, 토이푸들, 프렌치불독, 허스키 |
| `pet_profiles` 전용 | 2 | 코카스파니얼, 푸들 |
| 공통 | 12 | 골든리트리버, 래브라도리트리버, 말티즈, 보더콜리, 비글, 비숑프리제, 시바견, 시츄, 웰시코기, 진돗개, 치와와, 포메라니안 |

`코카스파니얼`↔`코커스패니얼`은 같은 견종의 표기 차이, `푸들`↔`토이푸들`도 같은 견종입니다.
나머지 6종(도베르만·미니어처닥스훈트·셰퍼드·요크셔테리어·프렌치불독·허스키)은 **한쪽에만
존재**합니다. 두 CSV가 서로 다른 견종 풀에서 생성됐다는 뜻입니다.

참고로 `DATAINFO.md` §2는 견종을 14종으로 적어두었는데, 이는 `pet_profiles` 기준입니다.
`pet_purchases`에는 20종이 들어 있습니다.

### 원인 추정 — `rating`은 정상이고 비정규화 컬럼만 어긋납니다

`DATAINFO.md` §4.1이 명시한 별점 신호 중 **목적·형태 매칭 신호는 살아 있습니다.**

```
목적·형태 매칭 487건 평균 4.26  /  비매칭 952건 평균 3.69
```

이 수치는 `pet_profiles.feeding_purpose`·`food_form_preference`를 조인해서 잰 값입니다.
즉 **`rating`은 `pet_profiles`를 제대로 보고 생성됐습니다.**

반면 `pet_purchases`의 `breed`/`weight_kg`/`allergy`는 96~99% 어긋납니다.
따라서 원인은 "두 파일이 통째로 무관"한 것이 아니라, **비정규화 컬럼을 채우는 패스가
`pet_profiles`를 참조하지 않고 독립적으로 값을 뽑았다**는 쪽입니다.

### 고칠 방법

비정규화 컬럼을 생성할 때 `pet_id`로 `pet_profiles`를 조회해 값을 **복사**합니다.
독립적으로 재추첨하지 않습니다. 대상 컬럼:

| `pet_purchases` 컬럼 | 원본 |
|---|---|
| `breed` | `pet_profiles.breed` |
| `weight_kg` | `pet_profiles.weight_kg` |
| `age_years` | `pet_profiles.age` |
| `allergy` | `pet_profiles.allergies` (§3의 표기 체계 통일 후) |
| `size_category` | `weight_kg`에서 유도 (§2 참고) |
| `age_group` | `age_years`에서 유도 |

## 2. `size_category`가 체중·견종과 모순 — 45건

```
O00091 프렌치불독 대형견 12.8kg   (기대: 중형)
O00124 토이푸들   대형견  3.2kg   (기대: 소형)
O00229 셰퍼드    소형견 39.2kg   (기대: 대형)
...
```

39kg짜리 "소형견"이 `build_doc()`을 거쳐 `"소형견 성견 셰퍼드..."`라는 문장으로 임베딩됩니다.

### 틀린 것은 `size_category` 컬럼 하나입니다

체중으로 유도한 체급과 견종으로 유도한 체급이 **서로 어긋나는 행은 0건**입니다.
즉 `weight_kg`와 `breed`는 1439건 전부 서로 맞고, `size_category`만 45건에서 어긋납니다.

| 체급 | 체중 범위 | 실제 데이터 분포 |
|---|---|---|
| 소형 | < 8kg | 2.0 ~ 7.0 |
| 중형 | 8 ~ 20kg | 8.1 ~ 19.8 |
| 대형 | > 20kg | 21.0 ~ 39.8 |

경계 구간(7~8kg, 20~21kg)이 비어 있어 판정이 깨끗합니다.

### 고칠 방법

`size_category`를 독립적으로 추첨하지 말고 **`weight_kg`에서 유도**합니다.
영향받은 견종은 15종에 걸쳐 있어 특정 견종의 문제가 아니라 유도 로직 부재의 문제입니다.

## 3. 알레르기 값이 성분명과 매칭 불가 — 205/288건

`GOAL.md`가 LLM 응답 항목으로 내세운 **"알러지 안전 여부"** 가 여기 걸려 있습니다.

상품의 성분 풀은 14종입니다:

```
고구마, 귀리, 글루코사민, 단호박, 닭고기, 소고기, 스피루리나,
연어, 오리, 오메가3, 유산균, 프로바이오틱스, 현미, 홍합추출물
```

### `pet_purchases.allergy` (문구 형태)

| 값 | 건수 | 매칭되는 성분 |
|---|---|---|
| `곡물 알레르기` | 108 | ❌ 없음 |
| `소고기 알레르기` | 69 | ✅ 소고기 |
| `특정 단백질 민감` | 61 | ❌ 없음 |
| `피부 알레르기 체질` | 36 | ❌ 없음 |
| `닭고기 알레르기` | 14 | ✅ 닭고기 |

### `pet_profiles.allergies` (성분명 형태)

| 값 | 건수 | 매칭되는 성분 |
|---|---|---|
| `없음` | 189 | — |
| `유제품` | 58 | ❌ 없음 |
| `닭고기` | 54 | ✅ 닭고기 |
| `소고기` | 53 | ✅ 소고기 |
| `곡물` | 50 | ❌ 없음 |

두 테이블이 **표기 체계부터 다릅니다.** 한쪽은 `닭고기 알레르기`라는 문구, 다른 쪽은
`닭고기`라는 성분명입니다. 문자열 비교로는 영원히 매칭되지 않습니다.

### 결과 — 별점 신호가 죽었습니다

`DATAINFO.md` §4.1은 알레르기 충돌 시 별점이 **평균 1.82**로 쏠린다고 명시합니다.
이 별점을 "이 반려견 조건에 이 상품이 얼마나 맞았는가의 결과물"이라 부르며 **추천 로직의
핵심 재료**라고 못박고 있습니다. 실측하면:

| 구분 | 건수 | 실측 평균 | 명세 |
|---|---|---|---|
| 알레르기 충돌 | 22 | **3.77** | **1.82** |
| 그 외 | 1417 | 3.87 | 3.78 |

충돌이 22건뿐인 것도, 그 22건조차 별점이 안 떨어지는 것도 문제입니다.
**별점을 근거로 삼는 추천 로직 전체가 지금은 근거를 잃은 상태입니다.**

### 고칠 방법

문제가 세 종류로 나뉘므로 각각 다르게 처리해야 합니다.

1. **표기 체계 통일** — `pet_purchases.allergy`를 문구가 아니라 **성분명**으로 저장하거나,
   표시용 문구와 판정용 성분명을 별도 컬럼으로 분리합니다.

2. **`곡물`·`유제품`은 매핑 표가 필요합니다.**
   `곡물`은 성분 풀에 `귀리`·`현미`로 존재하지만 문자열이 다릅니다.
   `유제품`은 성분 풀에 **아예 없습니다.** 알레르기 그룹 → 성분 목록 매핑 표를 만들거나,
   성분 풀에 해당 원료를 추가해야 합니다.
   (`DATAINFO.md` §2가 이미 이 주의사항을 적어두었으나 데이터에는 반영되지 않았습니다.)

3. **`특정 단백질 민감`·`피부 알레르기 체질`은 알레르기가 아닙니다.**
   성분을 특정하지 않는 체질 서술이라 어떤 성분 목록과도 매칭될 수 없습니다.
   `health_condition` 쪽으로 옮기거나 별도 컬럼으로 분리해야 합니다. 97건입니다.

## 4. `health_condition` 표기 흔들림 — 163종 (WARN)

같은 뜻이 여러 문구로 흩어져 있습니다. 28개 묶음이 검출됐고, 가장 큰 묶음은 8종입니다.

```
슬개골 건강에 신경 써야 함 / 슬개골 관리가 필요함 / 슬개골 상태를 주기적으로 확인 중 /
슬개골 탈구 있음 / 슬개골이 약한 편 / 슬개골이 약한 편임 / 슬개골이 약함 / 슬개골이 예민한 편
```

**임베딩에는 큰 문제가 아닙니다.** 표현이 흔들려도 의미가 비슷하면 벡터가 견딥니다.
문제가 되는 곳은 **SQL 선필터**입니다. `search.py`의 `FILTERS`처럼 값을 지정해 거르려 하면
`health_condition = '관절이 약함'` 조건이 나머지 3종의 변형을 놓칩니다.

### 고칠 방법

판정용 정규화 값(예: `슬개골`)과 표시용 문장을 분리하거나, 문구 템플릿 수를 줄입니다.
지금 당장 색인을 막지는 않으므로 §1~§3을 고친 뒤에 정리해도 됩니다.

## 5. `is_holdout` 전량 0 (WARN — 설계 미확정)

`DATAINFO.md` §4는 `is_holdout`을 "반려견별 가장 최근 구매 1건만 `1`"로 명세하고,
`load_db.py`도 holdout 건수를 출력하려 합니다. 실제로는 **1439건 전량 0**입니다.

**이것은 데이터 손상이 아니라 평가 설계가 아직 정해지지 않은 상태입니다.**
`config.py`의 `INDEX_FILTER`에 있는 `is_holdout = 0` 조건은 그래서 현재 아무것도 걸러내지 않습니다.

평가 방식이 정해져야 이 컬럼이 의미를 갖고, 그래야 추천 성능을 수치로 잴 수 있습니다
(`GOAL.md` 3부가 내세운 "정확도를 수치로 측정할 수 있습니다"가 여기 걸려 있습니다).

## 재생성 후 확인 절차

```bash
python src/load_db.py
python src/check_data.py     # ERROR 0건이어야 함
python src/build_index.py
```

`check_data.py`가 `ERROR 0건`을 낼 때까지 §1~§3을 고칩니다.
`WARN`은 남아도 색인을 진행할 수 있습니다.

새 견종이 추가되면 `src/check_data.py`의 `BREED_SIZE` 표를 갱신해야 합니다
(표에 없는 견종은 `ERROR`가 아니라 `WARN`으로 알립니다 — 표 갱신이 귀찮아서 검사 자체를
꺼버리는 일을 막기 위해서입니다).
