배포 스펙 · 오늘 뭐먹냥

dev-data-embed(백엔드/파이프라인)와 dev-web(프론트) 두 저장소를 Vercel · Render · Supabase · Docker 위에 올리기 위한 계획서. 아직 아무것도 배포되지 않은 상태에서 무엇을, 어떤 순서로, 왜 붙이는지 정리한 문서이며 이 문서 자체는 설정 파일을 대신하지 않는다 — 실제 render.yaml, vercel.json 등은 각 단계에서 사용자 확인 후 별도로 만든다.

00지금 상태

항목현재상태
백엔드 컨테이너화dev-data-embed/Dockerfile (python:3.12-slim, CPU torch)있음
백엔드 DBSQLite + sqlite-vec, 파일 하나(data/pet_reco.db)이전 필요
프론트dev-web/frontend/public/*.html 정적 HTML + JS (Next.js 아님)골격부터
인증FastAPI + JWT (dev-web AGENTS.md에 "추후 Supabase" 명시)계획됨
배포 설정 파일vercel.json / render.yaml / docker-compose 전무없음
즉 이번 작업은 "이미 돌아가는 배포를 정리"가 아니라 처음 올리는 것이다. 가장 리스크 큰 단계(SQLite → Supabase Postgres 이전)를 먼저 계획해두지 않으면 나중에 벡터 검색(recall@k)이 조용히 깨질 수 있다.

01왜 이 네 개인가

Vercel

프론트(Next.js) 전용 호스팅. 프리뷰 URL이 PR마다 자동 생성돼 이력서/포트폴리오에서 "링크로 바로 확인" 가능.

Render

이미 있는 Dockerfile을 그대로 올릴 수 있는 백엔드 호스팅. FastAPI + torch(CPU) 컨테이너처럼 무거운 이미지도 서버리스보다 안정적으로 상시 구동.

Supabase

Postgres + pgvector로 SQLite/sqlite-vec을 대체하고, JWT 자체 구현 대신 Auth를 붙여 "직접 만든 인증"에서 "관리형 인증"으로 스펙을 올린다.

Docker

로컬 개발 = Render 운영 이미지를 동일하게 유지하는 축. 새 팀원이 docker compose up 한 줄로 백엔드+DB를 띄우게 한다.

02서비스별 체크리스트

Render — 백엔드 (dev-data-embed)

  • render.yaml 추가: dockerfilePath: ./Dockerfile, healthCheckPath /health (이미 app/api/routes/health.py 존재 여부 확인)
  • 환경변수: .env에 있는 키 전부 Render 대시보드로 이전 (API 키는 절대 커밋 금지 — AGENTS.md Security 규칙)
  • DB 접속 문자열을 app/core/config.py에서 env로 뺀 상태인지 확인 (Supabase 이전 후 필수)

Supabase — DB + Auth

  • 스키마 이전: data/master/*.csv, data/seed/*.csv 적재 로직(pipeline.load_csv)을 Postgres 대상으로 재사용 가능한지 확인
  • 벡터: sqlite-vec BLOB(chunk_vectors) → pgvector 컬럼. 차원 수·거리 함수(cosine)를 eval golden으로 이전 전/후 recall@k 비교해서 회귀 없는지 검증
  • 인증: dev-web의 자체 JWT → Supabase Auth. app/core/auth.py의 토큰 검증 로직 교체 지점 확인

Vercel — 프론트 (dev-web)

  • 선행 조건: frontend/public/*.html 정적 페이지 → Next.js(App Router) 골격으로 전환 (dev-web/docs/DESIGN.md에 이미 FSD 레이어 설계 있음, 이번 리팩토링 대상)
  • NEXT_PUBLIC_API_BASE 같은 env로 Render 백엔드 URL 주입 (CORS는 rag-project-cleanup 참고 — REFERENCES.md 2번 항목)
  • Supabase 브라우저 클라이언트는 shared/api/에 한 곳으로 모음 (DESIGN.md 규칙 그대로)

Docker — 로컬 개발

  • docker-compose.yml: backend(FastAPI) + (선택) Supabase CLI 로컬 스택
  • 기존 Dockerfile은 그대로 두고 compose에서만 새로 추가 — 운영 이미지 변경 최소화

03진행 순서

리스크가 큰 것(데이터가 걸린 것)을 먼저 검증하고, 되돌리기 쉬운 것(프론트 호스팅)을 나중에 붙인다.

1
계층 구조 통일 — dev-data-embed / dev-web 리팩토링 먼저 마무리 (코드가 안정된 뒤에 배포 설정을 얹어야 재작업이 없다)
2
Supabase 스키마 이전 + recall@k 회귀 검증 — 가장 되돌리기 어려운 단계. eval golden으로 이전 전후 비교
3
Render에 기존 Dockerfile 그대로 배포 — 이미 있는 이미지라 새 코드 작성 없이 설정만 추가
4
dev-web을 Next.js 골격으로 전환 — DESIGN.md의 FSD 레이어를 실제 코드로 세움
5
Vercel에 프론트 배포, Render API 연결 — 마지막, 가장 위험 낮은 단계

04진행 전 확인이 필요한 결정

아래는 임의로 정하지 않고 다음 세션에서 하나씩 확인받을 사항.
  • SQLite → Postgres 이전을 완전 전환할지, 로컬 개발은 SQLite 유지하고 배포만 Postgres로 나눌지
  • Supabase Auth 도입 시점 — dev-web AGENTS.md의 "현재는 JWT" 상태를 이번에 같이 바꿀지, 별도 스텝으로 미룰지
  • docs/REFERENCES.md의 1번 참고 프로젝트(rag-project-cleanup) 기준과 이번에 새로 지정한 참고(RAG-learn)가 계층 이름에서 갈리는 부분 — 어느 쪽을 최종 기준으로 REFERENCES.md에 기록할지
