왜 SQL이 먼저인가

알러지·축종·체급은 타협 불가 조건이다. 유사도로 감점할 값이 아니라 후보에서 아예 빼야 한다. 벡터에 맡기면 “비슷하니까” 위험한 상품이 올라온다.

왜 벡터가 필요한가

“소형견 다이어트 사료” 같은 말은 컬럼으로 못 거른다. 후기 문장의 의미를 비교해야 한다.

왜 LLM이 마지막인가

후보 20건까지 좁혀 놓고 이유를 붙이는 일만 시킨다. 전체 상품을 넘기면 토큰도 낭비고 없는 상품을 지어낸다.

app 과 pipeline 을 나눈 이유

pipeline은 몇 분에 한 번 도는 배치, app은 요청마다 도는 서버다. 수명이 다르므로 배포 단위도 다르다. 그래서 둘이 공유하는 것(config·embedder)은 app/core/에 두고 pipeline이 그걸 가져다 쓴다 — 앱은 pipeline 없이도 떠야 하기 때문.

테스트·문서

pet_reco.db는 실제로 데이터가 들어가는 활성 트랙, user.db는 스키마만 만들어 둔 설계 트랙. 섞으면 “테이블은 있는데 데이터가 없다”가 된다.

큰 그림

화살표는 한 방향으로만 흐른다

이 저장소에서 “이 코드를 어디에 둘까”는 취향 문제가 아니라 무엇을 알아도 되는가의 문제다.

routes/       HTTP만 안다  (상태코드·검증)
   ↓
features/     순서를 안다  (무엇을 먼저 부를지)
   ↓
repositories/ 테이블을 안다 (SQL 한 줄)
   ↓
core/db.py    커넥션을 안다 (query · one · dicts)

domain/       아무것도 모른다 (계산·판정만)
adapters/     바깥 세계를 안다 (LLM · Supabase)
거꾸로 가면 생기는 일 — features/auth.py는 지금 app.core.db를 직접 불러 INSERT까지 한다. repositories/users.py는 같은 일을 하려고 만들어 두고 전부 NotImplementedError다. 두 자리 중 하나만 남겨야 나중에 “유저 저장 로직이 어디 있지”를 찾지 않는다.

domain이 DB를 모른다는 뜻

safty.judge()는 알러지 판정을 하지만 쿼리를 하지 않는다. 원료 id 목록과 알러지 id 목록을 인자로 받아 판정과 근거 문장만 돌려준다. 그래서 DB 없이도 테스트가 되고, 파이프라인과 서버 양쪽에서 같은 규칙이 돈다.

core/db.py 하나로 모으는 이유

커넥션이 여러 곳에 흩어지면 “어디서 커밋했지”를 못 찾는다. 다른 파일은 from app.core.db import query, one, dicts로만 접근한다.

1부 · 스키마와 SQL

DDL의 단일 원천 pipeline/create_schema/

테이블 정의가 여러 곳에 흩어지면 반드시 어긋난다. 그래서 DDL은 여기에만 있고, load_csv.py는 값만 넣는다. 문서 docs/schema/와 파일 구성이 1:1이다.

# execute_schema.py — 진입점
MODULES = (common_schema, user_schema, pet_schema,
           product_schema, purchase_schema)   # ← 이 순서가 생성 순서

DDL_KINDS = ('TABLES','INDEXES','UNIQUE_INDEXES','VIEWS')

def create_schema(db_path, verbose=True):
    con.execute('PRAGMA foreign_keys = OFF')   ①
    drop_all(con)                              ②
    for kind in DDL_KINDS:
        for ddl in collect(kind): con.execute(ddl)
    con.commit()
    con.execute('PRAGMA foreign_keys = ON')    ③
    for sql, rows in collect('SEEDS'):
        con.executemany(sql, rows)
    check_fk_targets(con)                      ④
  • ①DROP 중에는 FK를 끈다. 부모를 먼저 지워도 걸리지 않게.
  • ②모듈별 DROP 목록을 두지 않고 sqlite_master에 지금 실제로 있는 것을 지운다. 목록과 실제가 어긋나 옛 테이블이 유령으로 남았던 사고 이후의 선택.
  • ③PRAGMA foreign_keys는 트랜잭션 안에서 무시된다. commit 뒤에 켜야 시드의 자기참조 FK가 실제로 검사된다.
  • ④SQLite는 없는 테이블을 가리키는 FK로도 CREATE를 통과시킨다. 오타·순서 실수를 여기서 잡지 않으면 INSERT 때 터진다.

모듈 계약

각 *_schema.py는 TABLES / INDEXES / UNIQUE_INDEXES / VIEWS / SEEDS 중 있는 것만 모듈 수준 리스트로 노출한다. 없으면 빈 리스트로 친다.

순서가 정해진 이유

common(의존 없음) → user → pet → product → purchase.
테이블의 FK는 대상이 없어도 CREATE되지만 뷰는 안 된다. 그래서 pet·product를 함께 읽는 v_product_safety가 있는 product_schema가 뒤쪽이다.

SEEDS는 스키마의 일부

축종(개·고양이), 상품 대분류, 급여목적은 코드로 넣는다. CSV로도 빼면 같은 값이 두 군데 앉는다 — 그래서 load_csv.SOURCES에 이 테이블들이 없다.

1부 · 스키마와 SQL

DDL을 읽기 전에 알아야 할 규칙 7가지

전부 execute_schema.py 상단 docstring에 근거가 적혀 있다. 규칙을 알면 테이블 16개가 한 패턴으로 보인다.

1 · PK는 전부 INTEGER PRIMARY KEY

SQLite rowid 별칭이라 별도 인덱스가 안 생기고, 조인이 문자열 비교가 아니라 64비트 정수 비교가 된다. uint32 같은 폭 지정은 STRICT에서 에러다.

2 · 다대다는 두 FK를 묶어 PK

pet_breed_id 같은 번호를 붙이지 않는다. 조합 자체가 행을 가리키고, 중복 등록도 그냥 막힌다. 끝에 WITHOUT ROWID.

3 · 상태 대신 사실만 저장

탈퇴 플래그가 아니라 withdrawn_at, 비활성이 아니라 inactive_at. 상태는 계산해서 얻는다.

4 · 날짜는 TEXT ISO-8601

사전순 = 시간순이라 문자열 비교만으로 범위·정렬이 성립한다. 날짜 단독 인덱스는 안 만들고 (pet_id, purchased_at) 복합으로 만든다.

5 · 금액은 INTEGER(원)

REAL은 반올림 오차가 생긴다.

6 · 불리언은 INTEGER + CHECK IN (0,1)

SQLite에 BOOL이 없다. neutered, ingredients_verified, is_active, is_holdout이 대상.

7 · STRICT 테이블 — 끄지 않는다

'30000'   → 통과 (INTEGER 30000으로 저장)
'30000.0' → 통과
3.0       → 통과
'삼만원'   → 거부  cannot store TEXT
3.5       → 거부  cannot store REAL

그래서 CSV 로더가 int()로 미리 캐스팅할 필요가 없다. STRICT가 없으면 '삼만원'이 INTEGER 컬럼에 조용히 앉아 있다가 정렬에서 틀린 답을 낸다. 단, SQLite 3.37+가 필요해 구버전 파이썬으로 실행하면 malformed database schema로 죽는다.

후기는 구매에 매달린다

review.purchase_id가 PK이자 FK다. 구매 없이 쓴 후기는 DB가 받지 않는다 — “실제 후기에서만 근거를 찾는다”는 서비스 전제를 스키마가 강제한다. 구매 1건당 후기 최대 1건.

계정 삭제는 RESTRICT

pet.user_id가 CASCADE였다면 계정 삭제 한 줄이 pet → purchase → review를 타고 후기까지 지운다. 탈퇴는 withdrawn_at, 파기는 익명화 UPDATE. 행을 지우는 경로 자체를 DB가 막는다.

연결 테이블만 CASCADE

pet_breed·pet_allergy·product_ingredient처럼 부모 없이는 의미가 없는 행만 CASCADE, 마스터를 가리키는 쪽은 RESTRICT다.

SQL 해석 ①

다대다 테이블: 번호를 붙이지 않는다

CREATE TABLE pet_breed (
    pet_id   INTEGER NOT NULL
        REFERENCES pet(pet_id)     ON DELETE CASCADE,   ①
    breed_id INTEGER NOT NULL
        REFERENCES breed(breed_id) ON DELETE RESTRICT,  ②
    PRIMARY KEY (pet_id, breed_id)                       ③
) STRICT, WITHOUT ROWID                                ④

-- 역방향 조회를 위한 인덱스
CREATE INDEX idx_pet_breed_breed ON pet_breed(breed_id);   ⑤
pet_id │ breed_id
─────────────────
   3   │    1      초코 — 포메라니안  ┐ 믹스라 2행
   3   │    7      초코 — 치와와      ┘
   5   │    1      보리 — 포메라니안
  • ①펫이 지워지면 이 연결도 의미가 없다 → CASCADE.
  • ②품종 마스터는 다른 펫도 쓴다 → RESTRICT. 참조 중인 마스터 행 삭제를 막는다.
  • ③두 컬럼 조합이 이미 행 하나를 정확히 가리킨다. 별도 번호를 붙이면 “초코에게 포메라니안 두 번 등록”을 막는 UNIQUE 인덱스를 따로 챙겨야 하고, 빠뜨리면 중복이 조용히 들어간다.
  • ④PK가 곧 저장 순서가 되어 인덱스라는 별도 구조가 아예 생기지 않는다. 연결 테이블처럼 PK 말고 컬럼이 없는 표에 가장 잘 맞는다.
  • ⑤복합 PK는 앞 컬럼 기준으로만 정렬돼 있다.
    WHERE pet_id = 3 → PK를 그대로 탄다.
    WHERE breed_id = 1 → 못 탄다. “이 품종을 가진 펫 전부”를 쓸 거면 이 인덱스가 필요하다.

SQL 해석 ②

알러지 판정 뷰 v_product_safety

펫 × 상품 전량에 대해 안전 / 판정불가 / 위험 세 값 중 하나를 매긴다. 추천 파이프라인의 첫 관문.

CREATE VIEW v_product_safety AS
SELECT pt.pet_id, pr.product_id,
  CASE
    WHEN EXISTS (                          ①
        SELECT 1
          FROM product_ingredient pi          -- 상품의 원료
          JOIN ingredient_allergen ia
            ON ia.ingredient_id = pi.ingredient_id
          JOIN pet_allergy pa                 -- 그 펫의 알러지
            ON pa.allergen_id = ia.allergen_id
         WHERE pi.product_id = pr.product_id
           AND pa.pet_id    = pt.pet_id      ②
    ) THEN 'WARN'
    WHEN pr.ingredients_verified = 0
         THEN 'None'                        ③
    ELSE 'Safe'
  END AS verdict
FROM pet AS pt
JOIN product_animal_category AS pac
  ON pac.animal_category_id = pt.animal_category_id  ④
JOIN product AS pr ON pr.product_id = pac.product_id
WHERE pr.is_active = 1 AND pt.inactive_at IS NULL   ⑤
  • ①EXISTS는 “한 건이라도 있나”만 본다. 몇 개인지 세지 않으므로 첫 일치에서 멈춘다 — 존재 확인에 COUNT(*) > 0을 쓰지 않는 이유.
  • ②서브쿼리 안에서 바깥의 pr·pt를 참조하는 상관 서브쿼리. 그래서 판정이 “이 펫과 이 상품” 쌍마다 계산된다. 원료→알러지원→펫 알러지 세 단계를 이어 붙여 교집합이 있으면 위험.
  • ③모르는 것을 안전으로 처리하지 않는다. 원료표를 사람이 확인한 적이 없으면 안전이 아니라 판정불가다. 이 한 줄이 도메인 규칙 그 자체.
  • ④고양이에게 강아지 사료가 뜨지 않도록 축종부터 조인으로 좁힌다. 상품에 축종이 하나도 안 달려 있으면 그 상품은 아무에게도 안 뜬다(fail-closed) — 등록 UI가 필수값으로 받아야 하는 이유.
  • ⑤판매 중지 상품과 비활성 펫을 제외. 여기서도 상태 컬럼이 아니라 시각(inactive_at)으로 판단한다.

  • ③chunk_index로 순서를 남긴다. (purchase_id, chunk_index) 한 쌍이 조각의 식별자이고, 벡터도 이 쌍으로 붙는다 — 조각이 늘어나도 “원래 어느 리뷰였는지”를 잃지 않는다.

def build_where(profile):
    clauses, params = [f"r.rating >= {MIN_RATING}"], []
    for key, clause in FILTERS.items():
        value = profile.get(key)
        if not value: continue                       ①
        for item in (value if isinstance(value, list) else [value]):
            clauses.append(clause)                    ②
            params.append(item)
    return " AND ".join(clauses) or "1=1", tuple(params)  ③

# 결과 예시

params = ('소형', '닭', '소고기')
  • ①프로필에 없는 값은 조건을 만들지 않는다. 모르는 값에 NULL 비교를 걸면 전부 탈락한다.
  • ②알러지처럼 값이 여러 개면 같은 절을 값마다 반복해 AND로 묶는다. 하나만 걸면 나머지 알러지원이 든 상품이 그대로 통과한다.
  • ③조건이 하나도 없으면 1=1. 문자열 조립이지만 사용자 값은 절대 이어 붙이지 않고 전부 ? 바인딩이다 — SQL 인젝션이 들어올 자리가 없다.

4부 · 검증과 평가

홀드아웃 리뷰를 질문처럼 넣어 정답을 다시 찾아낸다 pipeline/eval/eval.py

# 1) 색인에서 빠진, 정답을 이미 아는 표본
WHERE r.is_holdout = 1 AND TRIM(r.body) <> ''          ①

# 2) 그 리뷰 본문을 질의로 던진다 — 검색 코드는 그대로 재사용
where, params = build_where({animal_category, size, allergy})
results = search(con, review, where=where, params=params, top_k=50)  ②

# 3) 정답 상품이 몇 위에 나왔나 — 정수 하나로 압축
rank = rank_of_answer(product_of, product_id, results)     ③

# 4) 지표
recall@k = (rank <= k 인 표본 수) / 전체
mrr      = 평균(1 / rank)                                   ④

이길 수 없는 표본을 따로 센다

정답 상품에 그 펫의 알러지 원료가 실제로 들어 있으면 알러지 필터가 정답 자체를 후보에서 뺀다. 검색 품질과 무관한 미스이므로 count_allergy_contamination()이 그 비율을 따로 찍는다 — 지표를 해석할 때 이 비율을 먼저 본다.

  • ①홀드아웃은 prep_rec.mark_holdout()이 고객별 최근 구매 1건을 ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY purchased_at DESC)로 고른다. “가장 최근 것을 맞혀 보라”는 추천 문제의 자연스러운 형태.
  • ②평가가 따로 검색 코드를 갖지 않는다. 실제 서비스와 다른 경로로 재면 그 숫자는 서비스 품질이 아니다.
  • ③recall@k도 MRR도 전부 이 정수 하나에서 파생된다. k마다 결과를 다시 훑을 이유가 없다.
  • ④recall@k만 보면 k 경계에서 우연히 갈린 표본에 결론이 휘둘린다. MRR은 순위를 통째로 반영해(1위=1.0, 5위=0.2) 흔들림이 덜하다.

4부 · 검증과 평가

차이처럼 보이는 것의 대부분은 표본 운이다

먼저 잡음의 폭을 잰다 — noise_band()

hits  = [1 if rank <= k else 0 for r in records]
rates = [복원추출로 다시 뽑은 recall@k] × 2000회
return 하위 2.5%, 상위 97.5%

표본이 66건이면 1건 = 1.5%p다. 이 폭 안의 모델 간 차이는 ‘차이’가 아니라 어느 리뷰가 홀드아웃으로 뽑혔느냐의 운이다. 모델을 고르기 전에 이 폭부터 안다는 순서가 핵심.

표본을 짝지어 비교한다 — compare.py

python -m pipeline.eval.compare \
    intfloat/multilingual-e5-small BAAI/bge-m3
  • 두 모델이 똑같은 질의를 풀었으므로 표본을 짝지어 “누가 어디서 이겼는지”를 센다
  • 뒤집힘이 6건 미만이면 부호검정상 우열을 말할 수 없다 → 비용 축(차원·속도)에서 고른다
  • recall 경계에 안 걸린 이동(43위 → 39위)도 신호로 함께 본다

결과를 DB 밖에 남기는 이유

모델을 바꿔 재색인하면 chunk_vectors가 DROP되므로 이전 모델의 결과는 DB에 남지 않는다. 그래서 data/eval/<모델명>.json으로 표본별 순위까지 저장한다 — 총점만 남기면 짝지어 비교할 수가 없다.
