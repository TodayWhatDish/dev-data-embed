- **의존 방향은 위→아래 한 방향이다.** `repositories` 는 `domain` 을 모르고, `domain` 은
  `repositories`/DB 를 모른다. 둘을 아는 건 `features` 와 조립 전담 파일(`domain_init.py`)뿐이다.

### 계층별 책임

| 계층 | 아는 것 | 모르는 것 | 왜 |
|---|---|---|---|
| `repositories/` | 테이블·컬럼 이름, SQL | 비즈니스 규칙, 마스터 캐시 | SELECT 만 하면 스키마가 바뀔 때 고칠 곳이 여기 하나로 좁혀진다 |
| `domain/` | 마스터 데이터(메모리), 판정·계산 규칙 | SQL, 커넥션 | SQL 을 모르면 자체검증(`tests/domain_and_repo/`)에 DB 가 필요 없다 |
| `features/` | 유스케이스 순서(선필터 → 랭킹 → 조립), profile 조립 | 테이블 이름 (원칙) | 유스케이스가 바뀌는 이유와 스키마가 바뀌는 이유가 다르다 — 한 파일에 안 섞는다 |

**밖(LLM)으로 나가는 글**에서 전화번호·이메일·주소·이름
같은 개인정보를 정규식으로 지운다. DB 저장값은 안 건드린다 — 마스킹은 되돌릴 수 없는 파괴적
변환이라 원본을 남겨야 나중에 정책이 바뀌어도 다시 처리할 수 있기 때문

### 정책: 완벽 차단이 아니라 "확실한 것만" 차단

 새는 쪽을 택한다. 사람이 손으로 다 거르지 못하니 자동 필터를 두는 거지, 완벽하게 막으려고
> 두는 게 아니다. 우회 수법을 다 쫓다 보면 규칙이 조여져서 평범한 후기가 먼저 지워진다.

### 문장째 지우지 않고 "그 부분만" 치환

연락 수단이 걸린 자리만 마크(`[전화번호]` 등)로 바꾸고 나머지 문장은 그대로 둔다.
문장 단위로 지우면 마침표 없는 글(당근마켓 스타일)에서 상품 설명까지 통째로 날아가고, `'배송 문의했더니
친절했어요'` 같은 평범한 후기도 오탐 한 번에 사라지기 때문 (`masking.py:9-11`). 이것도 위와 같은 "확실한 것만, 최소한만 건드린다" 원칙의 연장이다.
